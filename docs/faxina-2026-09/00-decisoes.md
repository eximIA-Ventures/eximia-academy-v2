| # | Tema | Decisão | Motivo |
|---|---|---|---|
| D1 | Domínio base | Env `NEXT_PUBLIC_APP_BASE_DOMAIN` (ex.: `academy.eximiaventures.com.br`). Host canônico de uma empresa = `{slug}.{base}`, derivado **por string, sem banco**. `tenant_domains` só guarda domínios próprios (ex.: `argos.eximiaacademy.com.br`). **[HUGO]** confirma o valor no EasyPanel. | Cadastro instantâneo; o banco só entra para domínio próprio (lacuna "middleware" da crítica). |
| D2 | Ordem de resolução do tenant por request | 1) `tenant_domains.host` (domínio próprio) → 2) subdomínio de `{base}` → 3) env `NEXT_PUBLIC_TENANT_SLUG` (modo legado de serviço único por cliente, lido no servidor em runtime) → 4) NEUTRO (`tenantId = null`). | O passo 3 mantém o serviço da Cory funcionando com as mesmas env vars até a virada. |
| D3 | Host × usuário divergem | Se o usuário tem `users.tenant_id` **ou** `user_tenant_memberships` no tenant do host, serve. Senão redireciona para o host canônico do tenant primário do usuário. super_admin: serve em qualquer host; a marca renderizada é a do tenant ativo (`x-sa-active-tenant`), com fallback para a do host. | R1 do plano corrigida pela crítica (`user_tenant_memberships` existe e está ativa na RLS). |
| D4 | Fonte da marca | Colunas novas `tenants.brand jsonb` e `tenants.modules text[]`, shape = `TenantConfig` **sem** `settings.customCSS`. Ordem: banco → env (runtime) → NEUTRO. `customCSS` nunca vem do banco para `dangerouslySetInnerHTML`. | Lacuna "customCSS" da crítica. |
| D5 | Slug neutro | `NEUTRO.slug` passa a ser `__neutro__` e entra na lista de reservados junto com `www, app, api, admin, central, academy, demo, neutro`. Resolução neutra devolve `tenantId = null`, nunca uma linha de `tenants`. | Colisão `demo` apontada pela crítica. |
| D6 | Plano default | `standard` (é o DEFAULT do banco). Drizzle e `feature-gate.ts` alinham a isso. | Três respostas conflitantes; o banco é a que vale em produção. |
| D7 | `apps/central` | **Removido** do monorepo (custa CI e não faz nada). O painel do super_admin vive em `apps/web`. | Crítica confirmou que ele roda no CI. |
| D8 | `/gauntlet-preview` | Não é urgente (404 em produção). Entra em `protectedPaths` com exigência de `super_admin` como defesa em profundidade, sem prioridade. | Refutado pela crítica. |
| D9 | Login | `/entrar` e `/login` continuam os dois por enquanto. `api/auth/validate-tenant` **fica** e passa a receber o slug resolvido por host (é a implementação pronta da regra D3 para o login legado). | Contradição interna apontada pela crítica. |
| D10 | Provisionamento | RPC `provisionar_tenant(...)` transacional + função `seed_tenant_defaults(tenant_id)` que semeia áreas, `notification_templates` e tudo que hoje é backfill único (`grep -l 'FROM tenants' supabase/migrations`). Trigger `AFTER INSERT ON tenants` chama a mesma função, para cobrir inserts manuais. Reutiliza `createTenantSchema` de `packages/shared/src/validators/whitelabel.ts` (com `initial_manager`). | Lacuna bloqueante "meia empresa" da crítica. |
| D11 | Convite / e-mails | `redirectTo` e links de e-mail derivam do host canônico do tenant (`lib/get-base-url.ts`, hoje sem chamadores, vira a função oficial). Nos 3 call-sites: `invite-user.ts`, `resend-invite/route.ts`, `notifications/nudge/route.ts`. **[HUGO]** cadastra `https://*.{base}/**` em Authentication → URL Configuration → Redirect URLs no Dashboard do Supabase; domínio próprio exige linha extra lá (documentado no guia EasyPanel). | Lacuna bloqueante "allowlist de Redirect URLs". |
| D12 | Storage `tenant-assets` | Bucket público só para `{tenant_id}/logo*` e `{tenant_id}/favicon*`; escrita de logo por admin do próprio tenant; `{tenant_id}/avatars/{uid}` gravável pelo próprio usuário. | Policies do plano quebravam o avatar do aluno. |
| D13 | Bootstrap do super_admin | Migration idempotente que promove o e-mail em `BOOTSTRAP_SUPER_ADMIN_EMAIL` a super_admin após o primeiro signup (função + trigger em `auth.users`). | Ambiente novo não tem quem abra a tela de cadastro. |
| D14 | M0 (replay do zero) | Migration com as 3 funções escrita a partir do que existe no repo/produção **[HUGO]**: sem Docker/psql aqui, o `supabase db reset` não pode ser validado nesta máquina. O SQL para extrair os corpos de produção fica em `05-tarefas-para-o-hugo.md`. | Limitação da máquina. |
| D15 | Microserviço `blueprint` | Interno-only: `allow_origin_regex` do domínio base, `Depends` verificando `INTERNAL_AUTH_TOKEN`, `tenant_id` do corpo só aceito se bater com o do proxy. `NEXT_PUBLIC_BLUEPRINT_MICROSERVICE_URL` sai da lista de env; `lib/blueprint-client.ts` e `blueprint-generator.tsx` (sem renderizador) saem. | Lacuna "CORS/auth zero". |

| D18 | Dockerfile | Saem os 16 ARG/ENV de marca e os 2 gates. Entram: `NEXT_PUBLIC_APP_BASE_DOMAIN` como ARG/ENV, e o gate novo (D17). Escopo real: 2 scripts + 3 testes (`verificar-marca.test.ts`, `verificar-marca-no-artefato.test.ts`, `dockerfile-roda-os-dois-gates.test.ts`); `marca-por-env.test.ts` vira teste do fallback. | Crítica corrigiu o raio. |
| D19 | Git | Nada é enviado ao remoto e nenhuma branch remota é apagada pelo orquestrador. Trabalho na branch local `faxina/app-unico`. Branches locais mergeadas em HEAD são apagadas **depois** de `git format-patch` em `/tmp/arquivo-morto/`. Stashes são exportados e mantidos. `GABARITO.json` é revertido para o HEAD (reseed não consolidado). | Ações externas são do Hugo. |
| D20 | Importar marca do ambiente | Rota `POST /api/admin/tenants/[id]/importar-marca-do-ambiente` (super_admin) copia as `NEXT_PUBLIC_TENANT_*` do serviço atual para `tenants.brand/modules`. Uso único no serviço da Cory antes da virada. | Os valores da Cory só existem no EasyPanel. |
| D21 | Instâncias da plataforma | "eximIA Academy" e "Argos Academy" são a **mesma imagem Docker**, cada uma num **serviço EasyPanel separado**, com seu **próprio projeto Supabase**, seu **próprio domínio base** e sua **própria marca neutra** (a que a porta de entrada `app.{base}`, empresas sem marca própria, e-mails, favicon e título usam quando não há tenant resolvido). A marca neutra da instância vem de variáveis `PLATFORM_*` lidas em **runtime, no servidor** (nunca `NEXT_PUBLIC_`, nunca build arg) — `PLATFORM_SLUG` (`eximia`\|`argos`, default `eximia`) mais `PLATFORM_BRAND_*`/`PLATFORM_FOOTER_TEXT`/`PLATFORM_SUPPORT_EMAIL`/`PLATFORM_MODULES`. Sem nenhuma `PLATFORM_*` setada, a instância é a eximIA Academy (NEUTRO, D5) — é o default, não uma instância "vazia". Ordem de mescla da marca passa a ser banco (D4) → env legado `NEXT_PUBLIC_TENANT_*` (D2 passo 3, um serviço por cliente) → marca da instância (`PLATFORM_*`) → NEUTRO eximIA. Argos **não é cliente, não é tenant e não é "parceiro" numa tabela do banco** (o modelo de `partners` cogitado em `10-parceiros-argos.md` foi descartado, ver D21 nesse documento): é **operadora de uma instância**, com `super_admin` próprio que cadastra as empresas dela dentro do Supabase dela, exatamente como a eximIA cadastra as dela. Dentro de cada instância o multi-tenant por host continua **exatamente como está** (D1–D5) — instância não é um nível novo de hierarquia, é qual processo/banco/domínio está respondendo. Qualquer personalização futura específica de uma instância (ex.: só a Argos ganha um módulo) entra como **flag lida de `PLATFORM_SLUG`**, nunca como branch nem fork de código. | Esclarecimento do Hugo em 2026-09-08: Argos não tem empresas "dentro" da eximIA — Argos é a própria plataforma rodando para outro operador, com seu próprio banco e sua própria porta de entrada. |
